# 客户端自动更新与发行约定

## 版本与兼容链

GitHub Release tag 使用 `<服务端主版本>.<服务端次版本>-<客户端版本>`，例如 `1.1-0.1.0`。tag 只写服务端版本的前两个数字，它们构成兼容链：服务端 `1.1.0`、`1.1.1`、`1.1.9` 共用 `1.1` 客户端链；服务端升到 `1.2.0` 后必须发布新的 `1.2` 客户端链。示例服务端版本 `0.1.0.alpha` 的 tag 前缀也是 `0.1`，例如 `0.1-0.0.1`。新 Release 使用短前缀；后端仍兼容解析以前使用完整服务端版本的 tag。

客户端版本独立递增。同一条服务端兼容链里，后续客户端版本必须大于前一个版本；切换到新的服务端兼容链时可以从新的客户端版本起点开始。后端选择当前服务端兼容链里客户端版本最高、且含有当前平台安装包的已发布 Release。Draft 和 GitHub 的 prerelease 标记 Release 不参与自动更新。服务端版本带有 `.alpha` 等后缀时，tag 前缀仍只写主、次版本号；完整服务端版本和预发布状态可写在 Release 标题或说明中，但不要勾选 GitHub 的 prerelease 选项。

## Release tag、标题与附件

以服务端 `1.1.0`、客户端 `0.1.0` 为例：

- **Tag：** `1.1-0.1.0`
- **标题：** `Futari Music 1.1.0 / 客户端 0.1.0`
- **说明：** 写明服务端兼容线 `1.1`、客户端变更和已知限制。
- **Windows 附件：** `FutariMusic-1.1-0.1.0-windows-x64.exe`
- **Ubuntu 附件：** `FutariMusic-1.1-0.1.0-ubuntu-amd64.deb`
- **后端附件：** `futari-1.1.0.jar`

后端按文件名后缀匹配两个客户端附件，并将其缓存到 `FUTARI_UPDATE_DIR/windows-x64/` 和 `FUTARI_UPDATE_DIR/ubuntu-amd64/`。客户端从配置的服务端检查并下载安装包；后端 JAR 作为服务器维护者的手动部署附件，不会由客户端更新器自动替换。每次更新客户端都要递增客户端版本并使用唯一 tag；服务端小版本升级时仍在同一兼容链发布，服务端次版本改变时开始新链。

在 GitHub 仓库的 **Releases → Draft a new release** 页面选择或创建上述 tag，填写标题和说明，上传对应平台的安装包及 JAR，然后发布正式 Release。更新轮询使用 GitHub Releases API，只处理已发布 Release；不要只创建 Git tag 而不发布 Release。GitHub 会为 Release 附件提供 SHA-256 摘要，服务端缓存后客户端会再次校验下载内容。[GitHub Releases API 文档](https://docs.github.com/en/rest/releases/releases)说明了 Release 列表及附件元数据的获取方式。

## 客户端构建版本参数

统一的客户端版本入口是 [Qt/FutariMusic/CMakeLists.txt](../FutariMusic/CMakeLists.txt) 中的 `FUTARI_CLIENT_VERSION`。不要在各个客户端源码文件里分别改版本；更新检查、当前客户端版本属性和 Release tag 都读取这个构建参数。CMake 默认值是开发版本；制作正式发行包时应在配置阶段通过 `-DFUTARI_CLIENT_VERSION=<版本号>` 设置客户端版本。已有 build 目录会缓存 CMake 参数，因此每次发行都要传入新值，或使用新的构建目录。服务端兼容参数推荐填写前两个版本数字：

```powershell
cmake -S Qt/FutariMusic -B Qt/FutariMusic/build-release `
  -DFUTARI_CLIENT_VERSION=0.1.0 `
  -DFUTARI_SERVER_COMPAT_VERSION=1.1
```

应用图标使用 `Qt/FutariMusic/icons/futari_icon_1024.png`。Windows 构建通过同目录的多尺寸 `futari_icon.ico` 和 `.rc` 资源写入 EXE；Ubuntu 构建会在 `cmake --install` 时安装 PNG 图标和 `.desktop` 启动项。CMake 同时把 PNG 编入程序，用作窗口图标。

Windows 默认静默参数为 `/S`，适用于 NSIS 安装器。后续确定安装器后，要把 `FUTARI_WINDOWS_INSTALL_ARGUMENTS` 设为该安装器的静默参数；例如 Inno Setup 可用 `/VERYSILENT /SUPPRESSMSGBOXES /NORESTART /SP-`。更新助手会等待当前进程退出、运行安装器并重新启动客户端。

Ubuntu 客户端下载 `.deb` 后通过 `pkexec apt-get install` 安装，系统会显示管理员授权界面；授权通过且安装成功后客户端自动重启。这个系统授权提示无法由应用的“静默更新”设置绕过。

## 服务端轮询与客户端行为

后端启动后立即在名为 `futari-update-poller` 的调度线程中扫描仓库 Releases，之后每 10 分钟轮询一次。客户端启动检查若赶在首次缓存完成前，会每 10 秒重试一次，最多重试 6 次。客户端更新目录默认为服务端进程工作目录下的 `updates/`，可通过 `FUTARI_UPDATE_DIR` 更改。更新元数据和安装包下载接口允许未登录访问，以便登录界面启动时也能检查更新；下载只允许返回服务端已缓存的当前平台 Release 附件。

客户端启动后检查服务端版本和兼容客户端版本。未开启自动静默更新时，发现新版本会显示确认窗口，确认后在窗口里显示下载进度；开启后自动下载与安装，并通过系统托盘通知更新开始、在托盘图标和提示文字中显示下载进度。Windows 安装器使用静默参数；Ubuntu 仍需用户完成系统授权。

服务端更新版本取自 Spring Boot 构建信息，即 `SpringBoot/pom.xml` 的项目版本。发布新服务端版本时应同步更新 POM 版本，并按该版本制作 JAR。更新检查本身不替代服务端部署：新 JAR 仍需由服务器维护者手动安装和重启。
