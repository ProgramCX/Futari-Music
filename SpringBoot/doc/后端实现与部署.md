# Futari Music 后端实现与部署

## 范围与决策

当前后端是单模块 Maven 项目，JDK 17、Spring Boot 3.5、MyBatis-Plus、MySQL 8、Redis、原生 WebSocket。包名为 `com.chengxu.futari`。按讨论结果，音乐文件使用本地内容寻址目录 + Nginx 内部重定向；房主可以通过接口授予或撤销在房成员的播放控制权。仅为 BCrypt 加入 `spring-security-crypto`。没有引入 MinIO、Spring Security Web、STOMP、springdoc 或音频元数据解析库。

实现为单个 Spring Boot 实例。房间热状态保存在 Redis，WebSocket 会话保存在此实例内存中；多实例部署需要引入跨节点消息分发和 Redis 原子状态脚本后再进行。后端不解析音频标签；桌面 Qt 客户端会读取支持格式的标签，并可提交经用户确认的 `title`、`artist`、`durationMs` 和专辑信息。没有标签时字段仍可手动填写，未提供时 `durationMs` 保持 `null`。

## 启动

1. 新数据库用 MySQL 8 执行 [`../sql/schema.sql`](../sql/schema.sql)。已有数据库按缺失版本依序执行 `001_song_metadata.sql`、`002_song_albums.sql`、`003_album_artist_identity.sql`。002 从旧 `song.album` 创建共享专辑并回填 `song.album_id`；003 增加专辑艺术家，并将专辑唯一身份由名称改为 `(name, artist)`，允许不同艺术家的专辑同名。保留旧字段供兼容；新 schema 不需要执行迁移。
2. 准备 Redis。复制 [`../.env.example`](../.env.example) 为 `SpringBoot/.env` 并填写配置；应用会从仓库根目录或 `SpringBoot` 模块目录按需读取该文件，也可直接在启动进程环境中设置变量。`JWT_SECRET` 必须是至少 32 字节的随机值，数据库密码需填写为实际值。不要把 `.env` 或生产密钥提交进仓库。
3. 使用 JDK 17 运行 `mvn test`、`mvn spring-boot:run`，或打包后运行 jar。默认 Spring 端口 8080。开发机若只有较新 JDK，可以用 `mvn -Dmaven.compiler.release=17 test` 验证，但生产运行环境以 JDK 17 为准。
4. 复制 [`../nginx/futari.conf.example`](../nginx/futari.conf.example) 到 Nginx 配置，将 `alias` 改为 `MUSIC_STORAGE_DIR` 的**绝对路径**，尾部保留 `/`，并保证 Nginx 可读该目录。生产环境推荐客户端使用 Nginx 地址（示例 8081）；代理会设置 `X-Futari-Nginx`，让下载通过 `X-Accel-Redirect` 由 Nginx 发文件并支持 Range。开发时也可直接使用 Spring 地址（默认 8080），此时 Spring 会受鉴权后直接流式返回歌曲并支持 Range。不要把 `/protected-music/` 设为公开目录。
5. 可在 `SpringBoot/.env` 设置 `BOOTSTRAP_ADMIN_USERNAME`（默认 `admin`）、`BOOTSTRAP_ADMIN_NICKNAME` 和至少 12 位的 `BOOTSTRAP_ADMIN_PASSWORD`。设置密码后，服务启动时若同名账户不存在，会用 BCrypt 创建管理员；同名账户已是管理员时默认不改动。若要把已存在的同名账户设为管理员并重置密码，可在**单次启动**时额外设置 `BOOTSTRAP_ADMIN_RESET_EXISTING=true`；启动成功后立即移除该变量或改回 `false`。此操作会撤销该账户当前登录令牌。不要把 `.env` 提交或把服务对外开放前仍保留引导密码。未设置引导密码时，数据库中的首个注册账户自动成为 `ADMIN`，后续账户为 `USER`。之后通过管理页面维护角色与权限。

数据库、Redis 或 JWT 配置缺失会导致启动或请求失败。`JWT_SECRET` 为空时应用主动拒绝启动。默认数据库/Redis 地址只是本地开发占位；密码从环境传入。

上传大小通过 `SpringBoot/.env` 配置：`FUTARI_UPLOAD_MAX_AUDIO_SIZE` 控制单个音频文件，默认 `64MB`；`FUTARI_UPLOAD_MAX_REQUEST_SIZE` 控制完整 multipart 请求，默认 `80MB`。接受 Spring `DataSize` 格式，例如 `128MB` 或 `1GB`。请求上限应大于音频上限并为封面、歌词和 multipart 开销留出空间。Nginx 示例中的 `client_max_body_size` 需不小于请求上限；改动 `.env` 后重启 Spring 服务，并同步更新、reload Nginx。

## 数据与权限

- `user` 保存 BCrypt 哈希、`role`、`can_upload`、`can_manage_server_playlist`。JWT 包含 `userId`、`jti`、过期时间；每次 REST 鉴权、WebSocket 握手和 WebSocket 上行消息都验证签名及 Redis `futari:login:{userId}` 的 jti。新登录替换旧会话；登出、管理员踢人或重置密码会删除登录态并关闭当前 WebSocket。
- `song` 按音频文件的 SHA-256 全站去重，磁盘文件名就是 64 字符 hash，不使用上传文件名作为路径。音频扩展名只允许 mp3/flac/aac/ogg/wav/m4a；单文件大小由 `FUTARI_UPLOAD_MAX_AUDIO_SIZE` 配置（默认 `64MB`）。相同音频再次上传时直接返回已有歌曲，**保留原歌名、歌手、专辑、歌词和封面**。数据库唯一索引保证去重。
- `album` 保存共享的专辑名称、专辑艺术家和封面；`song.album_id` 是可空外键，多首歌曲可以指向同一专辑。专辑唯一身份为 `(name, artist)`，同名不同艺术家可并存；名称相同且艺术家为空、又存在多个候选时服务端返回 `ALBUM_AMBIGUOUS`，不会静默关联错误专辑。`song.album` 暂作旧客户端兼容和搜索用的冗余名称。上传可用 `albumId` 选择现有专辑，或用 `newAlbumName/newAlbumArtist` 即时创建/复用专辑；共享专辑图字段为 `albumCoverFile`，单曲独立图字段为 `songCoverFile`，旧字段 `album`、`coverFile` 仍可用。
- 管理员可更新歌曲名称、歌手、歌词、专辑关联、音频和专辑图片，也可软删除歌曲。替换音频时保留歌曲 ID；若该音频 hash 已属于其他歌曲，返回歌曲重复错误。删除只逻辑删除歌曲，不立即清理内容寻址文件。编辑页选择已有专辑时可改专辑名或图片，这会影响同专辑的全部歌曲；新建专辑时不会修改原专辑。
- 歌词可用 `lyricsText` 直接传 UTF-8 文本，或用 `lyricsFile` 上传 UTF-8 `.lrc`/`.txt` 文件；两者不能同时提交，最多 256 KB。歌词保存在 `song.lyrics`，列表只返回 `hasLyrics`，详情通过单曲歌词接口读取。歌词文本可带 LRC 时间标签，后端原样保存，不解析时间轴。
- 专辑图片与单曲图片均用 `albumCoverFile` / `songCoverFile` 上传 JPEG、PNG 或 WebP，分别最多 5 MB。服务端同时检查扩展名和文件头，按图片内容 SHA-256 保存到 `{MUSIC_STORAGE_DIR}/covers/{hash}.{格式}`。`coverUrl` 为需 JWT 的相对 API 路径，专辑封面路径为 `/api/albums/{albumId}/cover`；旧单曲封面路径仍可读取。Qt 应通过带 Authorization 的网络请求读取图片，不能把它直接交给不带认证头的图片加载器。Nginx 代理时由 Nginx 内部重定向发图，开发直连 Spring 时由 Spring 返回图片内容。
- `room` 的名称、房主在 MySQL；`state` 为 JSON，`members`、`controllers` 为 Redis Set，`playlist` 为 Redis List。Redis key 均有 TTL；无成员时房间热状态在 10 分钟后过期。房间记录仍在 MySQL，重新加入可恢复一个空的热状态。
- 房主天然有控制权，且只能给在房成员授予控制权。`PLAY`、`PAUSE`、`SEEK`、`NEXT`、`PLAYLIST_UPDATE` 均校验房间成员与控制权。房主离开后不能远程授予权限，重新加入即可管理。每个用户同一时刻只能加入一个房间。
- 个人歌单仅本人可读写；服务器歌单所有登录用户可读，`ADMIN` 或 `can_manage_server_playlist` 可修改；上传需 `ADMIN` 或 `can_upload`。管理接口只允许 `ADMIN`。

## REST 约定

歌曲和封面二进制响应除外，其余成功响应为 `{"code":0,"message":"ok","data":...}`，失败为非零 `code` 和面向用户的中文 `message`。Nginx 代理时由 Nginx 发文件；开发直连 Spring 时由 Spring 流式返回。身份来自 `Authorization: Bearer <JWT>`，只有注册、登录免认证。时间值是 Unix 毫秒；分页参数 `pageNum` 从 1 开始、`pageSize` 默认 20 且最大 100。请求字段为 camelCase。下表中的 `{id}` 均为 Long 主键。

`RoomStateResponse` 结构：`{room:{id,name,ownerId,memberCount,createdAt},playback:{currentSongId,status,positionMs,serverTimestamp},songIds:[...],members:[UserResponse],controllerIds:[...],serverTime}`。首次播放前 `currentSongId=null`、`status="paused"`。

上传示例：表单字段 `file=@song.mp3`、`title=歌曲名`、`artist=歌手名`、`durationMs=180000`；可提交已有 `albumId=12`，或提交 `newAlbumName=专辑名`、`newAlbumArtist=歌手` 并附 `albumCoverFile=@cover.jpg` 创建/复用专辑；单曲图附 `songCoverFile=@song-cover.jpg`；歌词提交 `lyricsText=[00:01.00]歌词` **或** `lyricsFile=@song.lrc`。旧客户端也可使用 `album` 和 `coverFile`。使用 `multipart/form-data` 并附 Bearer token。单音频和完整请求上限分别由 `FUTARI_UPLOAD_MAX_AUDIO_SIZE`（默认 `64MB`）及 `FUTARI_UPLOAD_MAX_REQUEST_SIZE`（默认 `80MB`）配置；超限返回 HTTP 413 和可读错误信息。Nginx `client_max_body_size` 必须不小于完整请求上限。歌曲摘要包含 `albumArtist`，专辑项包含 `artist`；旧客户端可忽略新字段，音频下载路径不变。

## WebSocket 协议

### 歌单失效关联与解散房间（2026-10-09）

- 个人和服务器歌单列表、详情以及创建/修改响应通过 `SongService.findAvailableByIds` 批量读取有效歌曲并保留歌单顺序，跳过缺失或软删除歌曲，避免一条失效关联导致整个列表 HTTP 404（业务码 `1004`）。原关联保留，不删除用户数据；歌曲恢复后可重新出现在歌单中。排序同样针对有效歌曲校验。
- 解散房间先校验 MySQL 创建者身份，再逻辑删除房间，向当前成员广播 `ROOM_DELETED`，`data` 为 `{roomId}`，随后删除 Redis 房间状态、成员、控制者及共享队列。用户房间映射用 Lua 比较房间 ID 后删除，避免误删另一房间映射；当前房间恢复及加入接口可清理指向已删除房间的残留映射。不关闭账号 WebSocket 会话。
- 非创建者解散返回 HTTP 403、业务码 `5006`、消息「仅房间创建者可以解散房间」；不存在或已删除的房间返回 HTTP 404、业务码 `5001`。本次不新增数据库表或迁移。
- 后端 28 个测试通过，覆盖失效歌曲的个人/服务器歌单读取和排序、批量歌曲顺序、创建者离房后解散及非创建者权限拒绝。

连接：`/ws?token=<JWT>`。信封：`{"type":"PLAY","serverTime":毫秒,"data":{...}}`。所有下行消息带 `serverTime`。上行 `data` 不需要房间 id；服务端从已登录用户的当前房间定位。上行 `PING` 可在未入房时发送，`data.clientTime` 原样回显在 `PONG.data.echo`，同时返回 `PONG.data.serverTime`。

| 上行 | `data` | 下行效果 |
| --- | --- | --- |
| `PLAY` | `{songId,positionMs}` | 广播同类型，`data` 为完整播放状态 |
| `PAUSE` | `{positionMs}` | 广播暂停状态 |
| `SEEK` | `{positionMs}` | 广播新位置状态 |
| `NEXT` | `{}` | 按列表顺序循环切歌并广播 |
| `PLAYLIST_UPDATE` | `{songIds:[...]}` | 广播更新后的 id 数组；列表最多 500 首，不允许重复 id |

下行通知：`SYNC` 每 15 秒广播播放基准；`MEMBER_JOIN`/`MEMBER_LEAVE` 携带 `UserResponse`；`CONTROL_UPDATE` 携带 `controllerIds`；`INVITE` 携带邀请详情；`PARTNER_STATUS` 携带目标用户摘要；`KICKED` 携带原因；`ERROR` 携带 `{code,message}`。客户端根据 `positionMs + (当前服务器时间 - serverTimestamp)` 推进播放中的位置，建议只在偏差超过 500ms 时校准，避免频繁跳音。

## 已知边界

### 删除后重新上传歌曲（2026-10-09）

歌曲使用软删除，音频哈希仍受唯一索引约束。上传先查有效歌曲：有效记录存在则返回原记录，不覆盖元数据；不存在时查同哈希的软删除记录，并通过 `SongMapper.restoreDeleted` 条件更新恢复原 ID。此次提交的标题、歌手、专辑、歌词、封面、时长和上传用户全部写入，可选字段为空时也清空旧值，防止恢复错误歌词或封面。原 ID 的关联记录继续保留，无需删除用户数据或修改唯一索引。

上传数据库流程使用 READ COMMITTED 事务；并发恢复只有一个请求能把 `deleted=1` 更新为 `0`，其他请求读取已经恢复的有效记录。音频及封面文件使用内容哈希寻址，临时文件继续在 finally 中清理。此修复需要重启更新后的后端，无数据库迁移。

- 客户端负责真正解码、缓存和播放音乐；服务端只同步控制状态。
- 后端不解析音频标签；桌面 Qt 客户端使用 Qt Multimedia 读取元信息并把经用户确认的 `durationMs/title/artist/album` 提交给后端。媒体后端无法解析的格式仍可手动录入。
- 房间状态、成员与 WebSocket 会话为单实例设计；服务器重启后需重新加入房间，MySQL 房间记录和歌单仍在。
- 生产环境下载推荐经 Nginx 内部重定向；开发直连 Spring 也可下载，但会占用 Spring 工作线程和网络带宽。
